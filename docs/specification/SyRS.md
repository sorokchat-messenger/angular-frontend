# Frontend System Requirements Specification (SyRS) - SorokChat Messenger

> Цей документ описує цільовий стан frontend-системи (target design), а не поточний стан реалізації в src. Поточна реалізація може відрізнятися від описаного стану до досягнення MVP.

**Тип за ISO 15289:2019:** Specification

**Стандарт:** ISO/IEC/IEEE 29148:2018

> Цей документ описує вимоги лише до frontend-застосунку SorokChat.
> Взаємодія з API Gateway розглядається як зовнішній інтерфейс, а не як внутрішня логіка серверної частини.

## 1. Функціональні вимоги

### FR-01: Ідентифікація
Frontend повинен дозволяти користувачу створити обліковий запис
шляхом введення унікального ідентифікатора (login)
та пароля (password), а також відображати помилки валідації.

### FR-02: Аутентифікація
Коли користувач вводить коректні облікові дані, frontend повинен
надіслати запит до API Gateway, обробити відповідь, зберегти
стан авторизації та відобразити результат у UI.

### FR-03: Авторизація
Frontend повинен обмежувати доступ до чатів лише для учасників
відповідного чату на основі даних, отриманих від API Gateway.

### FR-04: Створення чату
Коли автентифікований користувач створює чат, frontend повинен
відправити запит на створення чату до API Gateway, оновити локальний стан
клієнта та показати результат дії користувачу.

### FR-05: Адміністрування чату
Адміністратор чату повинен мати можливість додавати та видаляти
учасників, змінювати ключ, видаляти чат через відповідні UI-дії
і оновлювати стан після відповіді API Gateway.

### FR-06: Управління ключами
Коли адміністратор ініціює ротацію ключа, frontend повинен:
1. Відобразити стан процесу ротації у UI.
2. Надіслати запит до API Gateway для ініціювання ротації.
3. Оновити локальний стан чату після успішної відповіді.
4. Показати подію в журналі аудиту та/або у відповідному UI-розділі.

### FR-07: Цифрові підписи
Frontend повинен підтримувати верифікацію цифрових підписів або
відображення статусу перевірки для критичних дій, отриманих від API Gateway.

### FR-08: Обмін повідомленнями
Коли користувач надсилає повідомлення, frontend повинен:
1. Зашифрувати текст симетричним ключем чату у браузері.
2. Обчислити MAC локально.
3. Надіслати повідомлення через WebSocket або API Gateway.
4. Відобразити повідомлення у UI відправника та показати статус доставки.

### FR-09: Офлайн-режим
Коли з'єднання втрачено, frontend повинен:
1. Показати кешовані повідомлення.
2. Ставити нові повідомлення в чергу.
3. Синхронізувати локальний стан після відновлення мережі.

### FR-10: Журнал аудиту
Frontend повинен відображати журнал критичних подій (вхід, ротація
ключа, зміна прав) у відповідному адміністративному розділі.

## 2. Нефункціональні вимоги

### NFR-01: Продуктивність
- Час відображення повідомлення: ≤ 200 мс після отримання даних від API Gateway.
- Час відображення стану ротації ключа: ≤ 5 секунд.

### NFR-02: Масштабованість
- Один чат: до 1000 учасників у UI-стані та списках.
- Один користувач: до 500 чатів у локальному інтерфейсі.

### NFR-03: Безпека
- Алгоритм симетричного шифрування у браузері: AES-256-CBC.
- MAC: HMAC-SHA-256.
- Криптографічні операції реалізовані у власних пакетах-обгортках над WebCrypto API.
- Refresh token зберігається в `HttpOnly` secure cookie.
- Локальні ключі шифрування та access token зберігаються виключно в IndexedDB.
- Приватні ключі та токени не зберігаються в localStorage/sessionStorage як основне сховище.
- Транспорт між frontend та API Gateway: HTTPS/WSS (TLS 1.3).

### NFR-04: Надійність
- Uptime frontend-інфраструктури: ≥ 99.5%.
- Стійкість до обривів мережі (офлайн-режим).

### NFR-05: Зручність
- Локалізація UI: українська (основна), англійська (додаткова).
- Адаптивний дизайн для екранів 320–2560 px.

### NFR-06: Супроводжуваність
- Стек: Angular + Feature-Sliced Design.
- Покриття unit-тестами ключової логіки: 100%.

## 3. Вимоги до інтерфейсів

- **UI:** веб-інтерфейс Angular.
- **Зовнішній інтерфейс:** API Gateway через REST + WebSocket.
- **Сховище клієнта:** IndexedDB для токенів, ключів і офлайн-кешу; localStorage лише для налаштувань UI.
- **Крипто в браузері:** власні пакети-обгортки над WebCrypto API, що реалізують AES-256-CBC та HMAC-SHA-256.

> У цьому документі не описується внутрішня логіка API Gateway, авторизація сервера або серверні алгоритми генерації токенів, ключів і журналів. Вони є зовнішніми залежностями.

## 4. Критерії верифікації

Кожна вимога FR-xx та NFR-xx має бути верифікована через:
- Unit-тести (для логіки frontend).
- Integration-тести (для API Gateway інтеграції).
- E2E-тести (для UI-сценаріїв).
- Security-аудит (для NFR-03).
