# Architecture Description - SorokChat Messenger

**Тип інформаційного елемента за ISO/IEC/IEEE 15289:2019:** Description

**Стандарт:** ISO/IEC/IEEE 42010:2022

**Версія:** 1.0

## 1. Ідентифікація системи

- **Назва:** SorokChat Messenger (frontend only)
- **Призначення:** веб-клієнт для безпечної комунікації в межах frontend-складу
- **Стек:** Angular, TypeScript, Feature-Sliced Design, WebCrypto API
- **Обсяг:** цей документ описує лише frontend-систему; backend, API, база даних, інфраструктура та серверні сервіси не є частиною архітектурного опису, за винятком зовнішнього контракту взаємодії через API Gateway
- **Не включено в scope:** серверна логіка, хмарні сервіси, база даних, управління розгортанням і внутрішня логіка авторизації

## 2. Зацікавлені сторони та їхні проблеми

## 6. Патерни та антипатерни

Патерни та антипатерни є частиною архітектурного опису відповідно до ISO/IEC/IEEE 42010:2022, оскільки вони відображають ризики, обмеження та правила реалізації, що безпосередньо впливають на прийняття рішень і відповідність цінностям системи.

### 6.1 Патерни, що допускаються

| ID | Патерн | Опис | Застосування | Міри безпеки / контролю |
|----|--------|-------|--------------|--------------------------|
| P-01 | Feature-Sliced Design (FSD) | Розбиття UI на шари `app`, `pages`, `widgets`, `features`, `entities`, `shared` | Весь frontend | Заборонено змішувати залежності між шарами навпаки або створювати циклічні імпорти |
| P-02 | Crypto wrapper | Криптографічна логіка винесена у власні пакети-обгортки над WebCrypto | AES-256-CBC, HMAC-SHA-256 | Криптографія реалізується лише в одному місці, а компоненти використовують API-інтерфейс |
| P-03 | Secure storage split | Refresh token у HttpOnly secure cookie; access token і ключі в IndexedDB | Сесійне управління та локальне шифрування | Не зберігати чутливі дані в `localStorage` / `sessionStorage` як основне сховище |
| P-04 | UI adapter layer | API-взаємодія із зовнішнім середовищем через адаптери/сервіси | Взаємодія з API Gateway | Компоненти не взаємодіють безпосередньо з низькорівневими HTTP/WS деталями |
| P-05 | Offline-first cache | Локальний офлайн-кеш та черга повідомлень | Повідомлення, синхронізація | Дані повинні мати явний статус `queued`, `sent`, `delivered` |

### 6.2 Антипатерни, що заборонені

| ID | Антипатерн | Ризик | Контрзаходи |
|----|------------|-------|-------------|
| A-01 | Cross-layer dependency in FSD | Порушення модульності, важка підтримка, хмарність логіки | Заборонені циклічні імпорти; залежність тільки зверху вниз |
| A-02 | Alias cross-import via `@x` | Порушення шарів FSD, «підміну» модульної структури, непередбачувана залежність між фічами | Всі alias-імпорти повинні бути прив'язані до шару: `@app`, `@pages`, `@widgets`, `@features`, `@entities`, `@shared` і не можуть обходити ієрархію |
| A-03 | Storage of secrets in browser local storage | Вразливість до XSS та витоку токенів / ключів | Вся чутлива інформація зберігається в IndexedDB або HttpOnly cookie |
| A-04 | Direct crypto usage in UI components | Порушення централізації безпеки, складне тестування | Використовувати лише crypto wrappers в сервісному шарі |
| A-05 | Security by UI only | Ілюзія захисту без загальнодоступної перевірки | Безпека повинна бути забезпечена на рівні схеми, політики та криптографічних обгорток |
| A-06 | Duplicate sources of truth | Конфлікти станів, помилки синхронізації | Єдиний джерело стану для токенів, ключів і офлайн-черги |
| A-07 | Frontend backend logic leakage | Порушення меж scope, некоректний розподіл відповідальності | Frontend описує лише UI/клієнтську логіку; backend-взаємодії є зовнішнім інтерфейсом |

### 6.3 Правила alias-імпортів (`@x`)

У FSD alias-імпорти є допустимими лише як механізм доступу до завчасно визначеного шару. Вони не повинні використовуватися як універсальний спосіб обійти архітектурні межі.

#### Таблиця дозволених і заборонених імпортів

| З шару | У шар | Статус | Коментар |
|--------|-------|--------|----------|
| `@shared` | `@entities` | Дозволено | `shared` служить базисом для типів і утиліт |
| `@shared` | `@features` | Дозволено | Для спільних утиліт та UI-блоків |
| `@shared` | `@widgets` | Дозволено | Для базових елементів інтерфейсу |
| `@shared` | `@pages` | Дозволено | Лише через явний інтерфейс, без прямої залежності від специфіки сторінки |
| `@entities` | `@features` | Дозволено | Сутності є джерелом даних для feature-логіки |
| `@entities` | `@widgets` | Дозволено | Для відображення даних в UI-компонентах |
| `@features` | `@widgets` | Дозволено | Feature може бути використана у вищих UI-абстракціях |
| `@features` | `@pages` | Дозволено | Сторінка об'єднує фічі та їхні сценарії |
| `@widgets` | `@pages` | Дозволено | Сторінки агрегують widgets |
| `@pages` | `@app` | Дозволено | App є верхнім контейнером для маршрутизації |
| `@app` | `@pages` | Заборонено | App не повинен залежати від нижчих шарів у зворотньому напрямку |
| `@pages` | `@shared` | Заборонено | Обхід ієрархії через верхній шар |
| `@app` | `@shared` | Заборонено | Не дозволяється прямий доступ до shared з верхнього шару без посередництва |
| `@features` | `@entities` | Заборонено | Feature не має залежати від нижчого шару, який уже є частиною його реалізації в зворотному напрямку |
| `@widgets` | `@features` | Заборонено | Між sibling-слоями без API-інтерфейсу |
| `@pages` | `@widgets` | Заборонено | Сторінка не повинна “обхідно” знижуватися до нижчого шару без явної композиції |
| `@features` | `@features` | Заборонено | За винятком явного shared-поділу або спільного API, не допускається cross-feature coupling |
| `@widgets` | `@widgets` | Заборонено | Не допускається безконтрольний cross-widget coupling |

#### Норма проекту
- Якщо модуль знаходиться нижче в ієрархії, він не повинен знати про верхні шари через alias.
- Усі виключення мають бути зафіксовані в ADR або в code review як виняток, а не як правило.
- `@x` не є “магічним доступом” до всього проєкту; це лише абстракція для визначених шарів FSD.

### 6.4 Відповідність стандартам

- Архітектурний опис визначає патерни та антипатерни як частину оцінки рішень щодо проблем зацікавлених сторін, що відповідає ISO/IEC/IEEE 42010:2022.
- Кожен антипатерн пов'язаний із конкретним concern і з архітектурним принципом, що забезпечує supportability, security, maintainability і traceability.
- Патерни і антипатерни є вхідними даними для ADR, перевірок і правок у вимогах.

## 7. Ключові архітектурні рішення (ADR)

| ID | Рішення | Альтернативи | Обґрунтування |
|----|---------|--------------|---------------|
| ADR-01 | Angular + FSD | React + Redux, Vue | Типізація, модульність FSD, підтримка enterprise |
| ADR-02 | Власні пакети-обгортки над WebCrypto API | пряме використання сторонніх crypto-бібліотек | Підтримка доменної логіки проєкту, чітке розділення криптографічної абстракції та браузерного API |
| ADR-03 | AES-256-CBC + HMAC-SHA-256 | ChaCha20, AES-256-GCM | Вимога проєкту: AES-256-CBC для шифрування, HMAC-SHA-256 для перевірки цілісності |
| ADR-04 | IndexedDB для токенів, ключів та офлайн-даних | localStorage, sessionStorage | Токени та ключі зберігаються в IndexedDB; локальне сховище є менш придатним для чутливих даних |
| ADR-05 | FSD-структура UI | монолітний компонентний підхід | Чітке розділення на app/pages/widgets/features/entities/shared |

## 8. Відповідності (Correspondences)

- Кожна функціональна вимога SyRS ↔ слайс FSD у SRS.
- Кожна безпекова вимога ↔ ADR-03 + WebCrypto.
- Кожен стейкхолдер ↔ хоча б одна точка зору.
