# Реєстр модулів - Sorokchat Messenger

## Мета

Цей реєстр описує основні модулі фронтенд-системи, їхню відповідальність та межі. Він слугує картою архітектури для розробників і AI-агентів і допомагає уникати змішування доменної логіки, UI-складових та інфраструктурних інтеграцій.

## Основні модулі

| Модуль | Відповідальність | Шар | Примітки |
|---|---|---|---|
| `app` | ініціалізація застосунку, маршрутизація, глобальні провайдери | Presentation / Application | верхній рівень композиції |
| `pages` | складання екранів | Presentation | агрегує widgets/features |
| `widgets` | повторно використовувані UI-блоки | Presentation | складені UI-фрагменти |
| `features` | бізнес-флоу користувача та поведінка функцій | Application | логіка конкретної функціональності |
| `entities` | доменні моделі даних і контракти стану | Domain / Shared | основні визначення стану |
| `shared` | повторно використовувані утиліти, UI-kit, криптографічні обгортки, інтерфейси адаптерів API | Shared | найнижчий спільний рівень залежностей |
| `infrastructure` | транспорт, persistence, адаптери безпеки | Infrastructure | зовнішні інтеграції |

## Обмежені контексти фронтенду

| Контекст | Обсяг | Відповідальні артефакти |
|---|---|---|
| Authentication | логін, реєстрація, захищені маршрути, стан сесії | `features/auth`, `pages/auth`, `entities/user` |
| Messaging | список чатів, історія повідомлень, офлайн-черга | `features/chat`, `features/message`, `entities/chat`, `entities/message` |
| Security | криптографічні обгортки, перевірка MAC, ротація ключів | `shared/crypto`, `features/rotate-key` |
| Offline | стан офлайн-черги, повтори, локальний кеш | `features/offline-queue`, `entities/message` |
| Admin | журнал аудиту та операційні панелі | `features/audit`, `pages/admin` |

## Межі модулів

- `shared` не може залежати від вищих шарів.
- `entities` не має залежати від UI або маршрутизації.
- `features` може залежати від `entities` і `shared`.
- `widgets` може залежати від `features` і `shared` лише через явні контракти.
- `pages` композиційно з'єднує нижчі модулі і не повинна приховувати бізнес-логіку.
- `app` координує маршрутизацію та глобальні провайдери, але не містить доменну логіку.

## Обмеження

- Заборонено пряме витікання backend-логіки в доменну модель frontend.
- Заборонено використання сирої криптографії безпосередньо в UI-компонентах.
- Чутливі дані мають залишатися в безпечному браузерному сховищі і ніколи не зберігатися в `localStorage` як основне місце.
- Залежності між модулями мають бути навмисними та задокументованими.

## Статус

Цей реєстр є стартовою картою для доменної декомпозиції та архітектурного опису. Він має залишатися синхронізованим із фактичною структурою фронтенду та оновлюватися при появі нових модулів або обмежених контекстів.
