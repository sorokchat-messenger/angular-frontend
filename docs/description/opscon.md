# Operational Concept (OpsCon) — SorokChat Messenger

> Цей документ описує цільовий стан системи (target design), а не поточний стан реалізації в src. Поточна реалізація може відрізнятися від описаного стану до досягнення MVP.

**Тип за ISO 15289:2019:** Description

**Версія:** 1.0

## 1. Призначення системи

SorokChat Messenger забезпечує безпечну комунікацію між користувачами
шляхом наскрізного шифрування, автентифікації, контролю цілісності
повідомлень (MAC) та контрольованого управління ключами.

## 2. Операційне середовище

- **Клієнт:** веб-браузер (Chrome, Firefox, Safari).
- **Зовнішній інтерфейс:** API Gateway через REST + WebSocket для доставки повідомлень у реальному часі.
- **Мережа:** публічний інтернет, можливі нестабільні з'єднання.
- **Офлайн-режим:** читання кешованих чатів, відправлення у чергу з
  доставкою після відновлення з'єднання.

## 3. Ролі користувачів

Ролі користувачів поділяються на дві групи: ролі на рівні додатка, ролі на рівні чату.

### 3.1. Ролі на рівні додатку

| Назва Ролі | Опис ролі | Права які надає роль |
|------------|-----------|----------------------|
| `USER` | Роль позамовчуваню при реєстрації | Створювати чати, писати у чати, додавати контакти |
| `PRO` | Роль яка надається після оформлення платної підписки | Права від `USER`, додаткові алгоритми шифрування |
| `PRO` | Роль для власнина сервісу | Повне керування сервісом |

### 3.2. Ролі на рівні чату

| Назва Ролі | Опис ролі | Права які надає роль |
|------------|-----------|----------------------|
| `MEMBER` | Роль яка видається автоматично після приєднання до чату | Читати, писати у чат |
| `ADMIN` | Роль адміністратора чату, вона призначається тому хто створив чат або тому кого обрав інший адміністратор чату | права `MEMBER`, зміна прав учасників, додавання чи видалення учасників, видалення чату |

## 4. Основні сценарії використання

### 4.1. Реєстрація та вхід
1. Користувач відкриває веб-клієнт.
2. Обирає реєстрацію або вхід.
3. Проходить автентифікацію (email + пароль, 2FA у майбутньому).
4. Отримує токен доступу та встановлену https куку із токеном відновлення.

### 4.2. Створення чату
1. Автентифікований користувач натискає «Створити чат».
2. Вказує назву, опис.
3. Система генерує симетричний ключ чату.
4. Запрошує учасників.

### 4.3. Обмін повідомленнями
1. Користувач вводить текст.
2. Клієнт шифрує його ключем чату, додає MAC.
3. Надсилає повідомлення через WebSocket або API Gateway.
4. Frontend отримує відповідь/подію від API Gateway та оновлює стан чату.
5. Клієнти отримувачів перевіряють MAC та розшифровують повідомлення у браузері.

### 4.4. Управління ключами
1. Адміністратор чату ініціює ротацію ключа через UI.
2. Frontend надсилає запит до API Gateway для ініціювання ротації.
3. Кожен учасник отримує оновлений ключ через відповідне API-сповіщення або відповідь сервісу.
4. Подія відображається у журналі аудиту в UI.

### 4.5. Офлайн-режим
1. Користувач втрачає з'єднання.
2. Нові повідомлення зберігаються локально у черзі.
3. Після відновлення з'єднання - синхронізація та повторне надсилання.

## 5. Обмеження та режими роботи

- Один чат: до **1000 учасників**.
- Один користувач: до **500 чатів**.
- Максимальний розмір повідомлення: **4096 символів**.
- Очікуваний час відповіді UI: **< 200 мс**.

## 6. Взаємодія із зовнішніми системами

- API Gateway — основний зовнішній інтерфейс для автентифікації, чату та подій реального часу.
- Push-сервіс (майбутнє, для мобільних клієнтів).
