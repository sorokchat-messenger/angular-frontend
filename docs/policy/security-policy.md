# Sorokchat Messenger - Політика безпеки

**Версія**: **1.0.3**

**Автор**: **Сороковський Андрій**

Цей документ визначає стандарти, правила та практики забезпечення безпеки для клієнтської частини месенджера "Sorokchat Messenger" (Angular / PWA).

---

## 1. Обсяг застосування
Ця політика поширюється на клієнтський веб-додаток, включаючи PWA (Progressive Web App), Service Worker, локальну базу даних клієнта IndexedDB (як єдине місцеве сховище даних) та взаємодію з бекенд-сервісами через REST API і WebSockets.

---

## 2. Управління автентифікацією та сесіями
- **Передача сесійних даних:** Для автентифікації використовуються HTTP-only, Secure, SameSite cookies або короткоживучі JWT Access-токени.
- **Збереження токенів:** Заборонено зберігати довгоживучі сесійні токени або паролі у відкритому вигляді в `localStorage` чи `sessionStorage`.
- **Обробка закічення сесії (401 Unauthorized):**
  - Автоматична спроба оновлення токера (`Refresh Token`) через HTTP-інтерцептор.
  - У разі невдачі — негайне розірвання сесії, очищення локальних даних та редірект на сторінку входу (`/login`).
- **Завершення сесії (Logout):** При виході з облікового запису обов'язково викликається ендпоінт бекенду для анулювання токенів та здійснюється повне очищення локальних сховищ клієнта.

### 2.1. Вимоги до форм авторизації та реєстрації
- **Мінімальний набір даних:** У форму входу або реєстрації дозволяється запрошувати лише ті дані, які є обов’язковими для автентифікації або створення облікового запису.
- **Зрозумілі запити:** На сторінках входу та реєстрації користувачеві має бути чітко пояснено, для чого збираються дані, які саме поля є обов’язковими, і як вони будуть використовуватись.
- **Згода користувача:** Перед відправкою даних форми система повинна забезпечувати явну згоду користувача на обробку персональних даних, якщо законодавство або внутрішні політики цього вимагають.
- **Валідація полів:** Усі поля форм автентифікації повинні проходити валідацію на стороні клієнта та сервера з метою запобігання введенню недійсних або шкідливих значень.
- **Шифрування та захист:** Дані, введені користувачем в форми логіну/реєстрації, не повинні зберігатися у відкритому вигляді в локальному сховищі без необхідного захисту; поля паролів мають бути приховані і не логуватися.
- **Безпечне надання доступу:** Сайт не повинен запитувати додаткові пов’язані дані (наприклад, платіжну інформацію, персональні дані поза межами авторизації) без явної потреби та попереднього пояснення.

## 3. Захист передачі даних (Data in Transit)
- **Захищений протокол (HTTPS/TLS):** Усі HTTP-запити до бекенд-сервісів повинні здійснюватися виключно через протокол HTTPS (TLS 1.2+).
- **Захищені WebSockets:** Для обміну повідомленнями в реальному часі використовується виключно захищений протокол `wss://`.
- **CORS та Передача персональних даних:** HTTP-запити використовують налаштування `withCredentials: true` лише з довіреними доменами бекенду.

---

## 4. Захист даних на клієнті (Data at Rest) та Криптографія
- **Локальні сховища (IndexedDB):**
  - Усі локальні дані додатка зберігаються виключно в IndexedDB.
  - Чутливі персональні дані користувачів та історія повідомлень зберігаються у зашифрованому вигляді та підлягають очищенню при виході з акаунта.
- **Криптографічні операції:**
  - Для виконання криптографічних операцій (шифрування, дешифрування, генерація ключів, підпис) використовується власна розроблена бібліотека.
  - Бібліотека містить типізовані обгортки (wrappers) над стандартизованими криптопримітивами (наприклад, Web Crypto API / SubtleCrypto), що забезпечує єдиний та безпечний інтерфейс роботи з ключами й шифруванням у клієнтській частині.
- **Логування в розробці:**
  - Заборонено виводити чутливі дані (токени, паролі, криптографічні ключі, персональну інформацію) у консоль браузера (`console.log`).
  - У продакшн-збірках логування має бути вимкнене або обмежене лише критичними помилками без персональних даних.

---

## 5. Захист від поширених веб-вразливостей (OWASP Top 10)
- **XSS (Cross-Site Scripting):**
  - Використання стандартних механізмів санітизації Angular (`DomSanitizer`).
  - Заборона використання `innerHTML` та методів `bypassSecurityTrust*` без попереднього ретельного обґрунтування та санітизації.
- **CSRF (Cross-Site Request Forgery):**
  - Захист забезпечується використанням `SameSite=Strict` або `SameSite=Lax` куків, а також Anti-CSRF токенів для модифікуючих запитів (POST, PUT, DELETE).
- **Clickjacking:**
  - Захист на рівні заголовків HTTP (`X-Frame-Options: DENY` або CSP `frame-ancestors 'none'`).
- **Open Redirects:**
  - Усі внутрішні перенаправлення (наприклад, після входу) здійснюються суворо за валідованими відносними шляхами додатка.

---

## 6. Політика Content Security Policy (CSP)
Для захисту від виконання стороннього шкідливого коду встановлюються наступні обмеження CSP:
- **`default-src 'self'`** — дозволено завантаження ресурсів за замовчуванням тільки з власного домену.
- **`script-src 'self'`** — заборонено виконання невідомих inline-скриптів (`unsafe-inline`) та `eval()`.
- **`style-src 'self' 'unsafe-inline'`** — використання стилів додатка з обмеженням зовнішніх джерел.
- **`connect-src 'self' https: wss:`** — дозволено з'єднання тільки з довіреними API та WebSocket ендпоінтами.
- **`img-src 'self' data: blob: https:`** — обмежене завантаження зображень та аватарів.

## 7. Безпека залежностей та збірки (Supply Chain Security)
- **Моніторинг залежностей:** Регулярна перевірка npm-пакетів на наявність відомих вразливостей за допомогою `npm audit`.
- **Оновлення фреймворку:** Своєчасне оновлення версії Angular та супутніх бібліотек до актуальних патчів безпеки.
- **Мінімізація зовнішніх залежностей:** Унікати додавання сумнівних сторонніх бібліотек для базового функціоналу.
