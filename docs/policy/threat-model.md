## Scope

Модель охоплює клієнтський застосунок Sorokchat Messenger, реалізований у Angular, включаючи сценарії авторизації, чату, обробки повідомлень, управління ключами шифрування, офлайн-кешу, локального сховища та взаємодії з API Gateway.

До розгляду входять:
- веб-клієнт Angular SPA;
- модулі авторизації, повідомлень, чату, офлайн-синхронізації та управління станом;
- обробка токенів, сесій, повідомлень та ключів шифрування;
- взаємодія з API Gateway через HTTPS;
- зберігання даних у IndexedDB, cookies та браузерній пам’яті;
- криптографічна логіка на основі WebCrypto API.

Поза межами моделі:
- внутрішня серверна логіка авторизації, повідомлень і баз даних;
- фізичний захист хостингу, серверів, мережевого обладнання;
- операційні процеси DevOps, резервне копіювання та інфраструктурний моніторинг;
- реалізація сторонніх сервісів, які розглядаються як зовнішні інтеграції, а не як частина фронтенд-архітектури.

> Модель охоплює лише frontend-частину Sorokchat, де критично важливо захищати токени, ключі, офлайн-стан і взаємодію з API Gateway. Серверний бекенд, база даних та інфраструктура розглядаються як зовнішній контекст, а не внутрішній об’єкт моделі.

## System Overview

Sorokchat Messenger — це веб-додаток для безпечної комунікації, де критичними є конфіденційність, цілісність повідомлень та захист локальних даних у браузері. Frontend складається з модулів у стилі Feature-Sliced Design: `app`, `pages`, `widgets`, `features`, `entities`, `shared`.

Основні потоки даних:
- користувач взаємодіє з інтерфейсом Angular SPA;
- SPA надсилає запити до API Gateway для входу, реєстрації, перегляду повідомлень та обміну даними;
- токени, ключі та офлайн-дані зберігаються в браузерному середовищі;
- чутливі дані шифруються перед зберіганням або передачею за допомогою WebCrypto API;
- повідомлення проходять перевірку цілісності за допомогою HMAC-SHA-256 або аналогічного механізму;
- офлайн-режим і черга повідомлень створюють додаткові ризики з точки зору локальної цілісності та повторного виконання дій.

**DFD (Data Flow Diagram)** використовується як основа для STRIDE-аналізу. У цьому документі виділяються такі елементи DFD:

- **External Interactor** — зовнішній користувач або інтеграційна система;
- **Process** — логічний модуль або сервіс, що виконує обробку;
- **Data Store** — сховище даних;
- **Data Flow** — потік даних між елементами;
- **Trust Boundary** — межа між середовищами з різним рівнем довіри.

### Елементи системи

| ID | DFD Type | Name |
| --- | --- | --- |
| E1 | External Interactor | User |
| E2 | External Interactor | API Gateway |
| P1 | Process | Angular SPA |
| P2 | Process | Auth / Session Manager |
| P3 | Process | Chat / Message Module |
| D1 | Data Store | IndexedDB |
| D2 | Data Store | Cookies / browser session cache |
| D3 | Data Store | Local storage / service worker cache |
| F1 | Data Flow | User -> Angular SPA |
| F2 | Data Flow | Angular SPA -> API Gateway |
| F3 | Data Flow | API Gateway -> Angular SPA |
| F4 | Data Flow | Angular SPA -> WebCrypto |
| F5 | Data Flow | Angular SPA -> IndexedDB |
| TB1 | Trust Boundary | Browser boundary |
| TB2 | Trust Boundary | API boundary |

### Основні зв’язки

- `E1 User` взаємодіє з `P1 Angular SPA` через `F1 User -> Angular SPA`.
- `P1 Angular SPA` надсилає запити до `E2 API Gateway` через `F2 Angular SPA -> API Gateway`.
- `E2 API Gateway` повертає відповіді до `P1 Angular SPA` через `F3 API Gateway -> Angular SPA`.
- `P1 Angular SPA` використовує `WebCrypto` як частину криптографічної обробки через `F4 Angular SPA -> WebCrypto`.
- `P1 Angular SPA` зберігає токени, ключі, офлайн-дані та чергу повідомлень у `D1 IndexedDB` через `F5 Angular SPA -> IndexedDB`.
- `TB1 Browser boundary` відокремлює локальний клієнтський стан від зовнішнього середовища.
- `TB2 API boundary` відокремлює клієнтський інтерфейс від серверної взаємодії з бекендом.

### Таблиця загроз

| Element | S | T | R | I | D | E |
| --- | --- | --- | --- | --- | --- | --- |
| **E1 User** *(External Interactor)* | Зловмисник може спробувати діяти від імені легітимного користувача, використавши викрадений сеанс або токен. | - | Користувач може заперечувати виконання критичних дій без достатнього журналу чи підтвердження. | - | - | - |
| **P1 Angular SPA** *(Process)* | Порушник може отримати доступ до клієнтської логіки або використовувати підроблений стан додатку. | Вхідні дані, повідомлення або локальний стан можуть бути змінені в браузері. | Відсутність журналювання дій у клієнті ускладнює встановлення відповідальності за критичні операції. | UI може відображати або розкривати дані, до яких користувач не має доступу. | Високе навантаження, помилки синхронізації або збій API можуть зробити застосунок недоступним. | Неправильна перевірка ролей або доступу може дозволити виконати недозволену дію в UI. |
| **P2 Auth / Session Manager** *(Process)* | Підміна сесії або повторне використання токена може дозволити зловмиснику діяти від імені іншого користувача. | Токени, refresh-дані або стан авторизації можуть бути змінені. | Без журналів або чіткого підписання дій важко довести, хто ініціював дію. | Витік токена або розкриття стану аутентифікації веде до компрометації сесії. | Серія помилок входу або скидання сесії може призвести до DoS для користувача. | Неправильна перевірка ролі або доступу може спричинити ескалацію привілеїв. |
| **P3 Chat / Message Module** *(Process)* | Зловмисник може намагатися від імені іншого користувача надсилати або видаляти повідомлення. | Повідомлення можуть бути модифіковані до передачі або після отримання. | Наявність “законних” дій не дає достатнього підтвердження авторства або моменту надсилання. | Вміст повідомлень або метадані можуть бути розкриті через помилки відображення або кешування. | Пошкоджене або перевантажене повідомлення може зупинити нормальну роботу чату. | Неправильна логіка ролевого доступу може дозволити перегляд або редагування чужих чатів. |
| **F2 Angular SPA -> API Gateway** *(Data Flow)* | - | HTTP- або WS-запити можуть бути змінені або підроблені на шляху. | - | Перехоплення токенів, сесійних параметрів або повідомлень може призвести до витоку даних. | Flood, timeout або зупинка запитів можуть спричинити блокування функціональності. | - |
| **F3 API Gateway -> Angular SPA** *(Data Flow)* | - | Відповіді можуть бути підмінені або змінені до рендерингу. | - | Дані користувача чи відповіді API можуть бути перехоплені або відображені не в тому контексті. | Перевантаження або відмова мережі може заблокувати синхронізацію. | - |
| **F4 Angular SPA -> WebCrypto** *(Data Flow)* | - | Підміна криптографічних параметрів або неправильне використання ключів може скомпрометувати цілісність даних. | - | Некоректна робота з ключами або обробкою даних може призвести до витоку вмісту. | - | - |
| **D1 IndexedDB** *(Data Store)* | - | Ключі, токени або офлайн-дані можуть бути змінені, пошкоджені або підмінені. | - | Несанкціонований доступ до IndexedDB або XSS-патерни можуть призвести до витоку чутливих даних. | Перевантаження або пошкодження сховища може зупинити роботу офлайн-режиму. | - |
| **D2 Cookies / browser session cache** *(Data Store)* | Підміна cookie або повторне використання session може дозволити зловмиснику увійти в обліковий запис. | Викрадений або змінений cookie може призвести до порушення сесії. | - | Небезпечне зберігання токенів у cookie без HttpOnly/Secure може збільшити ризик витоку. | Невірна конфігурація cookie може спричинити скасування сесії або блокування входу. | - |
| **D3 Local storage / service worker cache** *(Data Store)* | - | Дані у localStorage можуть бути змінені або пошкоджені. | - | Вміст повідомлень, ключі або стан аутентифікації можуть бути доступні для зловмисного скрипту. | Перевантаження або пошкодження кешу може зупинити синхронізацію. | - |

> STRIDE-категорії не є взаємовиключними: одна й та сама проблема може одночасно впливати на інформаційну безпеку, цілісність і контроль доступу.

## Threat Priorities

### Критичні загрози

1. **Викрадення токена або сесії**
   - наслідки: несанкціонований доступ до облікового запису;
   - контрзаходи: secure cookies, короткий TTL, обмеження на клієнті, перевірка сесій.

2. **Витік ключів шифрування або даних з браузерного сховища**
   - наслідки: розкриття вмісту повідомлень, компрометація офлайн-режиму;
   - контрзаходи: IndexedDB, WebCrypto, мінімізація даних, захист від XSS.

3. **Підміна повідомлення або записів у офлайн-черзі**
   - наслідки: порушення цілісності повідомлень, повторне виконання команд;
   - контрзаходи: HMAC/MAC, валідація вхідних даних, контроль статусів queued/sent/delivered.

### Середньої критичності

- неправильна перевірка ролей у UI;
- помилки в логіці авторизації або доступу до чатів;
- зловживання нестандартним кешуванням або відновленням стану з localStorage;
- нестабільність синхронізації при поганому з’єднанні.

### Низької критичності

- інтенсивне логування, яке розкриває метадані;
- неправильна локалізація або розмітка інтерфейсу без впливу на безпеку;
- відсутність нормалізованого оброблення невідомих помилок у UI.

## Key Security Controls

| Загроза | Контрзаходи |
| --- | --- |
| Spoofing | перевірка автентичності токенів, short-lived sessions, authorization checks |
| Tampering | MAC/HMAC, cryptographic wrappers, validation of message payloads |
| Repudiation | audit logs, controlled actions, explicit state transitions |
| Information disclosure | no secrets in code, secure cookies, IndexedDB, minimal data retention |
| Denial of service | request limits, offline queue protections, graceful error handling |
| Elevation of privilege | RBAC validation, FSD layer boundaries, no direct access to sensitive modules |

## Residual Risks

- браузерне середовище залишається вразливим до XSS та DOM-based атак;
- клієнтський код не має повного контролю над серверними механізмами безпеки;
- офлайн-дані та черги повідомлень можуть бути зловмисно змінені, якщо схема валідації недостатньо жорстка;
- неправильне використання browser storage може збільшити ризик витоку токенів і ключів.

Незважаючи на ці залишкові ризики, модель загроз Sorokchat вказує на те, що основні загрози зосереджені в трьох областях: автентифікація та сесії, захист повідомлень і ключів, а також безпечне зберігання даних у браузері. Для цих областей необхідно суворо дотримуватись вимог політики безпеки, архітектурних антипатернів і правил перевірки безпеки до релізу.
