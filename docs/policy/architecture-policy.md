# Sorokchat Messenger - Політика архітектури

**Версія**: **1.0.3**

**Автор**: **Сороковський Андрій**

> Для організації клієнтської частини ПЗ обрано архітектуру "Feature-Sliced Design" далі FSD.

FSD - це архітектурна методологія для проектування фронтенд-додатків (Angular, React, Vue чи Svelte), яка допомагає структурувати код так, щоб проект залишався масштабованим, зрозумілим та легким у підтримці з ростом команди та функціоналу.

Головна ідея FSD полягає у підході від предметної області (Domain-Driven) замість групування коду за технічними типами (файли не ділять просто на components, pages, redux тощо).

Проект за FSD ділиться на три основні виміри: Layers, Slices та Segments.

## 1. Layers (Шари)
Ієрархія шарів жорстко зафіксована: елементи вищого шару можуть імпортувати код тільки з нижчих шарів (знизу вгору імпорт суворо заборонений).
- `app/` — ініціалізація додатка (провайдери, глобальні стилі, роутінг).
- `pages/` — сторінки додатка, які збирають інтерфейс із віджетів чи фіч.
- `widgets/` — самостійні блоки сторінки (наприклад, Header, Sidebar, UserProfileCard).
- `features/` — бізнес-дії, що мають цінність для користувача (наприклад, SendComment, AddToCart, FilterProducts).
- `entities/` — бізнес-сутності предметної області (наприклад, User, Product, Order) з їхнім станом, UI та типами.
- `shared/` — перевикористовуваний код, не прив'язаний до бізнес-логіки (UI-кіт, API-клієнти, хелпери).

## 2. Slices (Слайси / Зрізи)
Всередині кожного шару (крім app та shared) код розбивається на зрізи за предметною областю.

Наприклад, у шарі entities можуть бути слайси user, chats, session.

У шарі features — register, login, search-chats.

Слайси одного шару не можуть напряму імпортувати один одного, що запобігає появі циклічних залежностей та каша-коду.

## 3. Segments (Сегменти)
Кожен слайс усередині ділиться на сегменти за технічним призначенням:
- `ui/` — компоненти та стилі.
- `model/` — бізнес-логіка, стейт, типи, селектори.
- `api/` — запити до бекенду та DTO.
- `lib/` — допоміжні функції, rxjs-оператори, хелпери, пайпи, директиви.

## 4. Ключові переваги
Public API (index.ts): Кожен слайс має єдину точку експорту. Інші частини додатка бачать лише те, що слайс дозволяє імпортувати.

Масштабованість: Можна легко додавати нові фічі чи видаляти старі, не боячись зламати інші частини системи.

Онбординг: Нові розробники швидко орієнтуються в проекті, бо структура прозора та стандартизована.

Специфічна позначка `@x` у контексті FSD та крос-імпортів використовується як внутрішній штамп / прапорець (cross-import notation) у шляхах імпорту для безпечного доступу до приватного або локального коду інших модулів у строго контрольованих ситуаціях.

Цей підхід детально описується в методології FSD при розв'язанні проблеми циклічних та перехресних залежностей.

За правилами FSD:
- Слайси одного шару (наприклад, `entities/user` та `entities/chat`) не мають права імпортувати один одного.
- Будь-який імпорт має йти через публічний інтерфейс — Public API (index.ts).

Але іноді виникає архітектурна колізія: Сутності тісно пов'язані бізнесом, але виносити їхню взаємодію у вищий шар (features або widgets) занадто складно або створює дублювання коду (Overengineering).

Символ `@x` (від англ. cross-import) використовується в назві сегмента або папки для створення спеціального «перехресного» Public API між конкретними модулями.

Уявімо дві сутності (entities): `user` та `chat`.
- Чат має відображати учасників (`user`).
- Профіль користувача має відображати його чати (`chat`).

Якщо вони будуть імпортувати index.ts один одного напряму, виникне циклічна залежність (`user` ⇄ `chat`).

## 5. Матриця імпортів у FSD

> **Важливо:** Будь-який дозволений імпорт має здійснюватися **виключно через Public API (`index.ts`)** відповідного слайса, якщо це не виняток із використанням точки входу `@x`.

| Модуль-ініціатор | Модуль-ціль | Статус | Обґрунтування / Правило |
| :--- | :--- | :---: | :--- |
| `app` | `pages`, `widgets`, `features`, `entities`, `shared` | ✅ | `app` — найвищий шар, що відповідає за ініціалізацію та збірку додатка. |
| `pages` | `widgets`, `features`, `entities`, `shared` | ✅ | Сторінка збирає UI-інтерфейс із нижчестоящих блоків. |
| `pages/A` | `pages/B` | ❌ | Сусідні слайси одного шару не можуть залежити один від одного. |
| `widgets` | `features`, `entities`, `shared` | ✅ | Віджети об'єднують фічі та сутності в самостійні блоки інтерфейсу. |
| `widgets` | `pages`, `app` | ❌ | Шар нижчого рівня не може знати про контекст вищих шарів. |
| `features` | `entities`, `shared` | ✅ | Фічі реалізують конкретні бізнес-дії над сутностями. |
| `features/A` | `features/B` | ❌ | Фічі мають бути повністю автономними та ізольованими. |
| `entities` | `shared` | ✅ | Сутності використовують загальні утиліти, UI-кіт та API-клієнти. |
| `entities` | `features`, `widgets`, `pages`, `app` | ❌ | Сутність предметної області не має залежити від сценаріїв використання. |
| `entities/A` | `entities/B` *(через main `index.ts`)* | ❌ | Прямий імпорт між сутностями створює циклічні залежності. |
| `entities/A` | `entities/B/@x/A` | ✅ | **Виняток `@x`:** лише через явно виділений cross-import Public API. |
| `shared` | `shared` *(всередині шару)* | ✅ | `shared` не має слайсів — це спільний набір незалежного коду. |
| `shared` | `entities`, `features`, `widgets`, `pages`, `app` | ❌ | `shared` є найнижчим шаром і має бути очищений від бізнес-логіки. |
| Будь-який шар | Глибокі файли слайса *(в обхід `index.ts`)* | ❌ | Порушення інкапсуляції (Private API). Доступ тільки через `index.ts`. |
