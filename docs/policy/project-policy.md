**Тип інформаційного елемента за ISO/IEC/IEEE 15289:2019:** Policy

> Ця політика визначає обов'язкові вимоги до коду та архітектури Sorokchat Messenger — безпечного веб-месенджера з E2E-шифруванням, фокусом на конфіденційності користувачів та чіткими межами відповідальності між шаром UI, бізнес-логікою та інтеграціями. Проєкт охоплює фронтенд-сервіс, його структуру, правила розробки та перевірки якості.

## Правила зміни політики

- Жодних змін мимохідь — політика не змінюється як побічний ефект іншої задачі; зміни вносяться лише окремою задачею на оновлення політики.
- Обов'язковий апрув — будь-яка зміна попередньо погоджується з власником проєкту або архітектурним лідером.
- Окремий коміт + інкремент версії — зміни політики йдуть окремим git-коммітом з префіксом `docs:` або `[POLICY]` та підняттям версії документа.
- Всі зрушення в правилах архітектури або безпеки мають бути зафіксовані в ADR або в релевантному документі проєкту.

## 1. Мета та цінності проєкту
Sorokchat Messenger — безпечний веб-месенджер для користувачів, які цінують приватність, контроль над ключами та безпечну взаємодію в реальному часі. Головна цінність — **приватність користувача понад усе**.

**Обсяг проєкту:** лише фронтенд. Серверна реалізація, база даних, API, інфраструктура та операційні сервіси не входять до цього документа, окрім зовнішнього контракту взаємодії через API Gateway.

**Не включено в цей scope:**
- серверна логіка авторизації та обробки повідомлень
- зберігання даних на backend-стороні
- інфраструктурне управління та деплой
- бізнес-логіка сторонніх сервісів, які не є частиною клієнтського проєкту

## 2. Принцип роботи із вимогами
1. Кожна вимога має бути оформлена за критеріями якості ISO/IEC/IEEE 29148:2018 (необхідна, однозначна, повна, сингулярна, здійснена, перевірювана, коректна, відповідна, доречна).
2. Кожна вимога має бути **трасованою** до бізнес-потреби та тесту.
3. Зміна вимоги оформлюється через Change Request (див. `request/`).
4. Усі вимоги до безпеки проходять обов'язковий review з боку security-експерта.

## 3. Принципи роботи із архітектурою
1. Архітектурний опис ведеться за ISO/IEC/IEEE 42010:2022.
2. Frontend реалізується за методологією **Feature-Sliced Design (FSD)**.
3. Стек: Angular (TypeScript).
4. Архітектурні рішення фіксуються у вигляді ADR (Architecture Decision Records)
   в `description/architecture/`.
5. Усі архітектурні рішення мають бути формально пов'язані з патернами та антипатернами, що описані в архітектурному описі.

## 4. Патерни та антипатерни

### 4.1 Дозволені патерни
1. **FSD-структура**: залежності лише зверху вниз; звернення між шарами виконується лише відповідно до FSD.
2. **Обгортки криптографії**: AES-256-CBC і HMAC-SHA-256 реалізуються через власні пакети-обгортки над WebCrypto API.
3. **Розділення сховищ**: refresh token у HttpOnly secure cookie; access token і ключі — у IndexedDB.
4. **Offline-first caching**: локальний кеш та черга повідомлень для офлайн-режиму.
5. **Адаптери зовнішніх інтеграцій**: API Gateway та WebSocket взаємодіють через адаптери, а не безпосередньо з UI-логікою.

### 4.2 Заборонені антипатерни
1. **Зберігання токенів або ключів у localStorage/sessionStorage** як основне сховище чутливих даних.
2. **Пряме використання криптографії в UI-компонентах** без централізованого сервісного шару.
3. **Порушення FSD-ієрархії**: імпорти з нижчих шарів до вищих, циклічні залежності або cross-import через `@x` без чіткого шару.
4. **Використання alias-імпортів як обходу FSD**: наприклад, `@pages` або `@app` імпортуються в `@shared` або feature cross-importи між sibling-слоями з метою обійти відповідний шар.
5. **Дублювання джерел істини** для токенів, ключів або статусів повідомлень.
6. **Ілюзія безпеки через UI** без захисту на рівні сховища, політик і криптографічної абстракції.
7. **Змішування frontend-логіки з backend-реалізацією** як частини архітектурного опису.

### 4.3 Правила `@x` alias-імпортів
1. Alias-імпорти дозволені лише в межах визначеного шару FSD.
2. Імпорт між шарами повинен зберігати ієрархію: `shared → entities → features → widgets → pages → app`.
3. Заборонені cross-importи між sibling-слоями через alias без явного API-інтерфейсу.
4. Усі винятки від правила мають бути обговорені та зафіксовані в ADR або code review.

### 4.5 Контроль виконання
- Кожен антипатерн повинен бути помічений у code review або in design review.
- Кожна зміна в безпеці або структурі має супроводжуватися перевіркою, чи не вводить вона новий антипатерн.
- Всі критичні архітектурні рішення фіксуються у формі ADR.

## 5. Принципи безпеки

1. **Zero-trust** - жоден компонент не довіряє іншому за замовчуванням.
2. **End-to-end шифрування** повідомлень у межах frontend-логіки, реалізоване через **AES-256-CBC** у власних пакетах-обгортках над WebCrypto API.
3. **MAC (Message Authentication Code)** для перевірки цілісності, реалізоване через **HMAC-SHA-256** у тих самих криптографічних обгортках.
4. **Контрольована зміна ключів** - з журналюванням і підтвердженням.
5. **Refresh token зберігається в HttpOnly secure cookie**.
6. **Access token та ключі шифрування зберігаються виключно в IndexedDB**. Не використовується localStorage/sessionStorage як основне місце для чутливих даних.
7. Паролі - не зберігаються у браузері.
